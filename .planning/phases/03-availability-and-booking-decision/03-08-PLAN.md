<objective>
Close the fault window in which a ready-to-book announcement becomes permanently unretractable, and stop a process-memory cache deciding what a user and an operator observe.

Purpose: `recordAnnouncement` is a post-send write with no compensation. When it fails, the message is live in the chat carrying a Mark-as-booked control while `announcementMessageId` stays null — and every correction path in the phase (`claimAnnouncement`'s retract branch, `retractStaleAnnouncement`, `closeBookedRound`, `dispatchAnnouncement`'s edit and retract branches) is guarded on that column being non-null. The orphan then goes on asserting that the rehearsal is ready to book after unanimity is lost and after the round is booked, and a post-cooldown re-announcement cannot clear it because the superseded pointer is null — producing the two-live-announcements state `03-04-PLAN.md` truth 10 forbids. No test covers the window (gap G-03). Separately, `editRoundMessage` reports a Telegram not-modified response as `edited`, so whether a repeat tapper sees the already-applied alert and whether an operator sees an unchanged-anchor line depend on a 128-entry process-global cache shared by every chat (review finding WR-05).
Output: `releaseAnnouncementClaim` on `PlanningService`, the answer path compensating a failed pointer write under a null-pointer guard (with the `/plan_status` re-post path deliberately excluded, D-33), a transaction-local read behind the retract-or-edit decision, an honest `unchanged` result, and the fault-injection cases that would have caught G-03.
</objective>

## Recorded decisions

**D-26 — the release restores the previous value under a compare-and-set; it does not null the column.**
D-18 says `readyAnnouncedAt` is never nulled and that the passage of the window is the release. That rule is about the ordinary lifecycle and it stands. This is a compensation for a claim that provably produced no addressable announcement, so the correct restoration is the value the claim replaced — null for a round's first announcement, the previous timestamp for a re-announce — carried on the round snapshot the answer transaction already returned. The write is guarded on the round still carrying the exact instant this dispatch claimed, so a claim won by somebody else in the meantime is never released by us. Reversibility: **reversible**.

**D-27 — the release is owned by the dispatch that made the claim, not by the service's write method.**
`recordAnnouncement` answers `stale` as well as `failed`, and only the caller knows which claim instant it is compensating. Putting the release inside the write method would need the pre-claim value threaded in anyway and would hide a durable write inside a method named for a different one. Reversibility: **reversible**.

**D-33 — the release is ANSWER-PATH ONLY. The `/plan_status` re-announcement deliberately does not release, and that asymmetry is the decision, not an omission.**
After `03-06-PLAN.md` the status path also wins a claim before it posts, which invites the symmetric treatment. It is wrong for two independent reasons.

*It would not fire.* The status path reaches the announcement slot only when `readyAnnouncedAt !== null` and the round is showing an announcement, so `announcementMessageId` is non-null; the release's guard requires it to be null. Specifying a release there would produce a branch that can never run and an acceptance criterion that can never pass.

*It would be harmful where it could fire.* On the status path the message DID land in the chat — the band was notified — and a failed `reanchorAnnouncement` leaves the round still pointing at its PREVIOUS announcement, which every correction path can still reach. Nothing is orphaned in the sense G-03 means: `repostAnchor` already strips the new copy's markup, and the round keeps an addressable announcement. Releasing a claim whose notification was delivered would hand back the window `03-06-PLAN.md` exists to hold, letting a second notification through inside thirty minutes — reopening G-01 through the compensation for G-03.

The null-pointer condition in the guard is therefore not incidental — it is the whole discriminator, and it splits the answer path's own failure into two sub-cases that both come out right:

| Pre-claim `announcementMessageId` | What the fault leaves | Release | Why |
|---|---|---|---|
| null — a round's FIRST announcement, or one whose earlier pointer was never recorded | a live copy nothing can address; every correction path dead until the window elapses | fires | this is the state G-03 names, and escaping it is worth one extra notification |
| non-null — a post-cooldown re-announce | the PREVIOUS copy still addressable and still pointed at, the new copy stripped by Task 2 | refused | correction paths all still work, the band was notified, and handing the window back would permit a second notification for nothing |

Reversibility: **reversible** — the guard and the call site are one line each.

**D-28 — a Telegram not-modified response is `unchanged`, and the fingerprint cache is demoted to a request-saver.**
The two edit call sites branch on the result in opposite directions, so the cache deciding the result made both branches non-deterministic. After this change the cache can only skip a request; it can never change an answer. `03-04-PLAN.md`'s statement that a not-modified is absorbed is unchanged — what changes is what the absorption is called. Reversibility: **reversible**.

**D-29 — `recordAnnouncement` drops its unused clock parameter rather than acquiring a write for it.**
IN-02 offered both. The parameter's stated justification was that a future timestamp column should not have to change callers' shape; `releaseAnnouncementClaim` now demonstrates the clocked write on this very path, so the justification no longer holds and the honest form is the smaller one. Reversibility: **reversible** — re-adding a parameter is a signature edit.
