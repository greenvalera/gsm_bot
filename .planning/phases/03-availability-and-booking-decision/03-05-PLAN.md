## Recorded decisions

**D-19 — the booking confirm/keep pair is actor-unbound (RESEARCH Open Question 3, recommendation taken).**
Phase 1's roster-removal precedent binds its confirm/keep pair to the requester. Booking deliberately does not. D-13 exists so that no single person is a point of failure for recording a fact that is already true, and binding the pair would mean the administrator who opened the confirmation is the only one who can complete it. The pair's `CallbackAction.actorUserId` is written as a placeholder because the column is NOT NULL; the planning route declares route-resolved actor binding so the boundary never compares it, and the (author OR fresh administrator) check is re-run inside `applyBooking`. **A reviewer must not "fix" this toward the roster-removal precedent.** Reversibility: reversible — binding it later is a `where` clause.

**D-20 — the booked confirmation does not name who booked.**
`bookedByUserId` is recorded durably for Phase 4 and for operator forensics, but the chat message says the rehearsal is booked without naming the person. Nothing in LIFE-01, D-14 or D-16 asks for the attribution, and omitting it avoids both an extra identity read on the close path and one more place a member's label is written into permanent group history. Reversibility: reversible.

**`requestBooking(chatId, actorId, callbackToken, now, role)`** — the role arrives as an already-resolved `CurrentTelegramRole`, resolved by the handler at tap time through the non-destructive current-role lookup and passed in exactly as `dispatchTakeover` passes it. In one `$transaction`, copying `takeover`'s ordering:
  1. Re-read the `CallbackAction` by token; re-validate kind, chat and expiry; require an unconsumed row; parse the target and require the book-request action.
  2. Read the round; require the `chatId` match; return `already-booked` when its status is the booked label and `stale` for anything other than confirmed.
  3. Eligibility: `round.authorUserId === actorId || isAdministratorRole(role)` — otherwise `not-eligible`. This is a read-only refusal and it happens before anything is written, so a refused tap leaves the control spendable for whoever may legitimately press it next.
  4. Re-read the participants and re-derive `availabilityOutcome`; anything other than the all-available value is `unanimity-lost`. Cheap, and it stops a confirmation being opened in front of a slot that has already died.
  5. `mintBookingConfirmationActions` and return `offered`. The request row is NOT consumed — a person who opens a confirmation and walks away must be able to open another.

**`keepBooking(chatId, actorId, callbackToken, now, role)`** — same skeleton; the read-only refusals first, then consume the keep token with the `consumedAt: null` compare-and-set asserting one affected row (`duplicate` otherwise), then return `kept` with the round, participants and a freshly minted book-request action so the restored announcement has a live control.
