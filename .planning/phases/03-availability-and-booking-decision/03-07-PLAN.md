<objective>
Make every capability this phase calls standing genuinely standing: created once, loaded everywhere else, returned in a deterministic order, and never minted for a round that could not use it.

Purpose: three defects share one root. `keepBooking` and the announcement post branch re-mint the `book-request` row that `loadAvailabilityActions` was built to load (gap G-02), so live rows grow without bound across request/keep cycles and post-cooldown re-announcements; `loadAvailabilityActions` has no `orderBy`, so the last-row-wins collapse in `controlTokens` picks between them non-deterministically and falsifies the render fingerprint (gap G-02, and the one probe edge a gap invalidates); `mintTakeoverAction` gained no status guard when D-03 widened `/plan_status` from drafts to every recoverable position, so the phase's most open command INSERTs an unusable takeover row on essentially every request (gap G-04); and `requestBooking` mints a fresh confirm/keep pair on every tap while never revoking the previous one (review finding WR-06).
Output: an ensure-then-mint lookup for the booking capability, a total order on the availability action lookup, a draft guard on the takeover mint, a supersede-then-mint confirmation pair, and the integration cases that prove each bound.
</objective>

## Recorded decisions

**D-23 — the standing booking capability is ensured, not consumed and not swept.**
G-02 has two possible closures: stop creating extra rows, or expire the old ones. Ensure-then-mint is taken because it is the one that makes the count *answerable* rather than merely eventually-small: after it, the invariant is "at most one live `book-request` row per round", assertable in a single query at any instant. Expiring on re-mint would leave the count correct only between sweeps and would keep the render fingerprint moving. Reversibility: **reversible**.

**D-24 — the deterministic order is `createdAt` then `token`, ascending.**
`CallbackAction`'s primary key is `token`, so `[{ createdAt: "asc" }, { token: "asc" }]` is a total order over the table with no new column and no new index. Ascending rather than the descending order `status()` uses for rounds, because `controlTokens` collapses last-row-wins: ascending means the newest row wins, which is the behavior a reader of that loop would expect. The order matters even once D-23 bounds the booking rows at one, because the two answer rows are also collapsed through the same map. Reversibility: **reversible**.

**D-25 — the superseded confirmation pair is expired, never deleted.**
WR-06's fix expires the previous `book-apply` / `book-keep` rows by setting `expiresAt` to the transaction's clock, inside the same transaction that mints the replacement. Deleting them would erase the audit trail the token-release tests read and would race the retention sweep; expiring them makes the callback boundary refuse the orphaned token before the dispatcher runs, which is already the established refusal shape. Reversibility: **reversible**.
