## Gap Closure Context

This plan closes the second half of **G-01-6 / finding F-4 / broken window 12**, and writes the
missing execution record for plan 01-14.

**Cause 2 of the F-4 AND-gate — NEUTRALISED SEAM.** Exactly one update-path error seam is wired,
`bot.catch` at `main.ts:50-59`, and it is confirmed reachable under the runner. It never fires
because twelve catch clauses across the three feature handler modules discard the exception without
binding it, converting every failure into user-facing copy. Two of them —
`roster-handlers.ts:260` and `:291` — are total black holes whose own comments state that Telegram
delivery itself failed and there is no further recovery to attempt. A delivery failure is exactly
the class of defect an operator needs a log line for. Because the redactor emits name, message and
code only when an error object is passed under the error key, an unbound exception is not merely
unlogged — it is unloggable.

The twelve sites are `setup-handlers.ts:314`, `:385`, `:418`; `settings-handlers.ts:235`, `:257`,
`:308`, `:400`; `roster-handlers.ts:139`, `:210`, `:233`, `:260`, `:291`.

**Cause 3 of the F-4 AND-gate — VERIFICATION DESIGN.** Runbook step 2e and UAT test 6 assert
"grepping the logs for coordinates returns nothing, BECAUSE the update path logs through the
redacting logger" — an existential premise no plan requirement backed. Plan 01-21 added the
automated guard; this plan makes the manual check mirror it.

**Plan 01-14 has no SUMMARY.** Its Task 1 (redacted logger and CI gates) is complete and committed;
its Task 2 (live Telegram verification) ran, returned a NOT APPROVED verdict, and produced findings
F-1 through F-9. Without a SUMMARY, 01-14 is invisible to the history digest and its roadmap entry
can never be reconciled. It is written here, at the end of the gap-closure wave, so it can record
both what 01-14 delivered and where each of its findings was closed. It must NOT claim the live
verification passed.
