<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| replied Telegram message → durable identity | Nested `from` may be absent, bot-owned, anonymous, or unrelated to typed command text. |
| roster command/callback → current administrator check | Listing and every mutation require fresh external authorization. |
| opaque removal token → membership transaction | Token is untrusted; initiator/chat/target/expiry authority remains server-side. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-01-18 | Spoofing | `/roster_add` target identity | high | mitigate | Accept only non-bot `reply_to_message.from`; never build membership from typed text/username. |
| T-01-19 | Tampering | removal replay/cross-target | high | mitigate | Initiator/chat/target/expiry-bound action, fresh authorization, one transaction, and single consumption. |
| T-01-20 | Elevation of privilege | roster action | high | mitigate | Revalidate current administrator at list/add/request/confirm boundaries; denial discards actor drafts. |
| T-01-21 | Information disclosure | fallback identity | medium | mitigate | Expose only final four ID digits in UI and keep full identity/action authority server-side. |
| T-01-SC | Tampering | installed packages | high | mitigate | Use the approved lockfile and add no dependency in this plan. |
</threat_model>
