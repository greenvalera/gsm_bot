## Root cause evidence

Application-source search found no `migrate_to_chat_id` or `migrate_from_chat_id` handling. `src/telegram/handlers.ts` declares command, text, location and callback routes, without a migration route. `SettingsService.getCommitted` (`src/domain/chat/settings-service.ts:187`) and `PlanningService.status` (`src/domain/planning/planning-service.ts:4149`) read configuration by the incoming exact chat ID. The schema independently scopes configuration, roster membership, rounds, prompts and callback actions by chat ID. Telegram changed the chat identity; the application did not move or resolve its existing state.

Recovery must preserve the original configuration, roster and history; simply running setup again would hide the migration defect and strand the old state. A fix needs idempotent migration handling, a deliberate policy for old message anchors/callbacks and a safe recovery path for this already-observed migration. Test duplicate/out-of-order migration updates and target-state collisions before applying recovery to the retained database.
