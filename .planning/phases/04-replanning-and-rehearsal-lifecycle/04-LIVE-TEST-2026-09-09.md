## Finding G-04-1 — displaced announcement retains contradictory facts

Severity: major. Related acceptance: H2, H4/H5 lifecycle recovery and P09.

Reproduction: confirm a one-person round; answer Cannot attend then Can attend; send `/plan_cancel`; choose Keep rehearsal; answer Cannot attend again. The availability card and current announcement correctly show blocked, while the earlier announcement still tells the group everyone can attend and to book the rehearsal. It has no buttons, but its text is still an active claim rather than a historical/moved notice.

Expected: when a lifecycle command relocates the control surface, every displaced outcome announcement must become clearly historical or be corrected on later transitions. A group must not see contradictory current booking advice for the same attempt.

Browser evidence identifiers are Telegram Web DOM `data-mid` values, not Bot API message IDs. The initial availability/stale announcement/current announcement were DOM 398383/398384/398386 (Bot API 195/196/198). The Saturday cancellation evidence is DOM 398393/398394/398396/398397 (Bot API 205/206/208/209): the first, third and fourth say cancelled, while the second still says booked. The database's tracked Saturday pointers are 205 and 208, explaining why message 206 is not corrected. No message links are inferred from client-local IDs.

### Root cause

`deliverLifecycleConfirmation` in `src/telegram/planning-handlers.ts` calls `reanchorLifecycleConfirmation`, then renders the previous current outcome with no buttons. `PlanningService.reanchorLifecycleConfirmation` replaces either `anchorMessageId` or `announcementMessageId`. Subsequent answer corrections, `deliverSuccessor`, and cancellation effects can only reach the retained pointers. The previous message remains in Telegram but has no persisted route for future updates. `repostAnchor` also retires cards by copying current text through `clearSupersededCard`, so the same invariant must cover status recovery.

Plan 04-06 addresses this single root cause across H2, H4 and H5. Diagnosis and plan checking were performed inline; no independent subagent review is claimed. No application fix was applied during verification.
