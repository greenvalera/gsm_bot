<objective>
Repair CR-01 in `src/domain/auth/authorization-service.ts:34-53`: an unbound `catch` collapses "Telegram did not answer" into "this actor is not an administrator", and the shared denial path then hard-deletes both of the actor's drafts. A transient 429 during `/setup` therefore wipes a *current* administrator's eight-step wizard and tells them something false — while logging nothing, so an operator cannot tell the two cases apart either.

Purpose: this is blocking the live Telegram verification run of phase 01. Runbook step 5 (demotion / AC-4) drives exactly this code path. If a 429 lands mid-run, the draft vanishes, the bot refuses, and the run records a false PASS for AC-4 — the same class of non-probative evidence as finding F-4, which this phase already spent plan 01-22 closing.

Output: three behaviour changes in one small domain class, the logger threaded from the composition root, and the two directions of the branch pinned separately in the unit suite.

The only thing that moves is *what else* the failure path does: it stops deleting drafts, and it starts logging.
