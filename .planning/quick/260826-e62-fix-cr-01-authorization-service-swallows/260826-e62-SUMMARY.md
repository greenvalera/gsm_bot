# Quick Task 260826-e62: Fix CR-01 — AuthorizationService Swallows Lookup Failures — Summary

A membership lookup that throws now denies without deleting the actor's drafts and emits one error-level line carrying the bound exception under `err`; the fail-closed denial itself is unchanged.

## What Was Built

`src/domain/auth/authorization-service.ts:34-53` had an unbound `catch` that collapsed "Telegram did not answer" into "this actor is not an administrator". Both cases then fell into the same denial path, which hard-deleted the actor's `setupDraft` and `settingsEditDraft` rows. A transient 429 during `/setup` therefore wiped a **current** administrator's eight-step wizard, told them something false, and logged nothing — so an operator could not tell the two cases apart either.

Three changes, in one small domain class plus the composition root:

1. **The failure path split from the denial path.** The caught value is now bound, and `PermissionDeniedError` is thrown from inside that same clause. The two `deleteMany` calls sit lexically below it and are structurally unreachable when the lookup failed.
2. **The failure is logged.** One `logger.error` line carrying `event`, `chatId`, `actorId`, a bounded `outcome`, and the caught value under `err` — the only key `sanitizeFields` renders structurally. Error level, matching the 01-22 classification: an infrastructure/Telegram failure is error-level, an expected-input rejection is debug-level.
3. **The logger arrives by constructor injection.** `createBot` hoists the existing substitution (`deps.logger ?? createLogger({ level: "silent" })`) into a single `const` and passes that one instance to both `registerChatReadinessHandlers` and `new AuthorizationService(...)`. No module-level singleton, no optional-logger check inside the class.

The unit suite now pins both directions of the branch separately, so neither can regress silently.

## Security Invariant: Preserved

The fail-closed denial **stays**. Unavailable membership evidence still denies and still throws `PermissionDeniedError`. No retry, no permit-on-failure path, no configuration knob. Both the retained `unavailable` case in the original test and the first assertion of the new test pin it. The only behavioural change is that the destructive cleanup no longer runs on that path, and that the swallowed exception is now recorded.
