Write the file in English (project constraint: all project and planning documentation is English, regardless of the language the requester uses in chat). Write it as an operator checklist, not as a design document: second person, imperative, one action per checkbox. Assume the operator has a terminal, a Telegram account that is an administrator of the private test group, and a second human on a second Telegram account — and assume nothing else.

Use exactly these top-level sections, in this order.

1. Title `# Phase 01 — Live Verification Runbook`, followed by a short intro naming what this closes: the Plan 01-14 Task 2 blocking human-verify checkpoint, which is Outstanding Evidence Gap 1 in `01-VALIDATION.md`. State that Gaps 2, 3, and 4 in that file are separate regression-gate defects and are not covered here, so a red test suite is not a failure of this runbook.

2. A prominent warning block, before any instruction, titled to make it unmissable, covering the privacy-mode trap: Telegram privacy mode stays ENABLED for this bot by locked project decision. A bot in a group with privacy mode enabled only receives commands, replies to its own messages, and service messages. Therefore a plain location message will never reach the bot and the timezone step will appear dead. The operator must send the location as a REPLY to the bot's own step prompt message. State plainly that this is expected behavior and not a defect, so the operator does not stop and report the bot as broken. Repeat the same instruction inline inside Step 2 where the location is actually sent.

3. `## Prerequisites` — a checkbox list the operator completes before starting: a dedicated test bot created through BotFather with its token in hand; a private Telegram group used only for this test; the bot added to that group as an ADMINISTRATOR (required because `getChatMember` is only reliable for other users when the bot is an administrator); a second human on a separate Telegram account present in the group and able to post a message; `POSTGRES_PASSWORD` and `BOT_TOKEN` exported in the shell; Docker and Docker Compose available. Add a line telling the operator to keep the real bot token out of any file they commit and out of any observation they paste into planning evidence.

4. `## Start the bot` — the launch command using Compose service names and environment interpolation from `compose.yaml`, run from the repository root, building first. Note that `postgres` must pass its health check and `migrate` must complete successfully before `bot` starts, so the first run is slower. Give the log-follow command. Then give a DANGER note that the restart used later in Step 2 restarts the bot service only, and that the operator must never tear the stack down with the volume-removing flag, because the named PostgreSQL volume holds the exact persistence this checkpoint is proving.

5. Six sections with headings of the form `## Step 1`, `## Step 2`, ... `## Step 6` — the heading must start with `## Step ` followed by the digit, then a short title. Map them one to one onto the six `how-to-verify` steps from 01-14-PLAN.md Task 2:
   - Step 1: unconfigured `/setup` prompt, `Start setup`, and the first wizard step.
   - Step 2: location to committed timezone, the full eight-step wizard, review order, save, bot restart, `/settings` re-read, and the log inspection for raw coordinates.
   - Step 3: one valid single-setting edit, then a conflicting schedule that must commit nothing.
   - Step 4: `/roster_add` as a reply to the second human, safe identity display, removal confirmation, keep once, then remove, then a repeat tap.
   - Step 5: draft started as administrator, that account demoted in Telegram, next protected command and next protected callback both denied, draft discarded, re-promotion does not resume it.
   - Step 6: long roster, empty roster, and error states — wrapping, no full numeric ID exposure, no reply keyboard and no WebView, authoritative message replacement after callbacks.

   Give every step the same internal shape:
   - `### Do` — numbered checkbox actions, each one concrete enough to perform without interpretation (which account acts, which command, which button).
   - `### Expect` — the exact strings and button labels, quoted verbatim from `01-UI-SPEC.md`, in fenced or inline code so whitespace and punctuation are unambiguous. Mark bold headings as bold, name buttons by their exact label, and where the spec fixes an order (review field order, settings section order, weekday keyboard rows) state that order explicitly.
   - `### Record` — a blank fill-in line for what was observed and a PASS/FAIL choice, for example an `Observed:` line with an underscore rule and a `Result: [ ] PASS  [ ] FAIL` line. Every step gets one.

   Copy required for the `Expect` blocks, all sourced from `01-UI-SPEC.md`:
   - Unconfigured prompt: bold `Set up rehearsal planning`, body `This chat is not configured yet.`, single button `Start setup`.
   - Resumed wizard prompts begin `Setup in progress` and show `Step X of 8`.
   - Timezone card: bold `Time zone found`; one candidate renders `Candidate: <IANA zone>` with one `Use <IANA zone>` button; multiple candidates render `Candidates:` with every zone code-formatted and one `Use <IANA zone>` button per zone; the card ends with `Send another location`. State the two invariants: the bot never auto-picks the first result and never offers typed-zone entry.
   - Time prompts: `Send a time in 24-hour format, for example 19:30.`
   - Wizard order, all eight values: timezone from location, weekday as inline `Mon` through `Sun` in two rows of four then three, start time in `HH:MM`, duration in whole minutes, daily start in `HH:MM`, daily end in `HH:MM`, reminders showing the default pair `10:00 and 16:00` with `Use defaults` and `Edit times`, and planning access as `Admins only` / `Previous participants` / `Anyone in chat` defaulting to `Admins only`.
   - Setup review: bold `Review configuration` with labelled values for time zone, default day, default start, duration, daily start, daily end, reminder times, and planning access, then `Save configuration` followed by `Cancel setup`.
   - Settings dashboard: bold `Chat settings` with sections in the fixed order `Schedule`, `Availability reminders`, `Planning access`, committed values only, one `Edit …` button per editable value or pair.
   - Single-setting review: bold `Review change` with `Current: <old>` and `New: <new>`, buttons `Save change` and `Keep current value`.
   - Schedule validation: `daily start < daily end` and `default start + duration <= daily end`; on failure the bot names the conflict, re-prompts only the offending field, keeps the other valid draft values, and the copy is `That schedule does not fit inside the daily time boundaries. No changes were saved.`
   - Invalid time input: `Use 24-hour time in HH:MM format, for example 19:30.`
   - Roster: bold `Band roster`, alphabetical, entries rendered as `• <Telegram name> — @username`, or `• <Telegram name>`, or `• Telegram user ••••<last 4 ID digits>`, each with one `Remove member` action.
   - Empty roster: heading `No band members yet`, body `Reply to a member's message, then send /roster_add to add them.`, final line `Reply to a member's message, then send /roster_add.`, and no Remove controls.
   - Roster add: `✅ Added <member> to the band roster.` and, when already active, `✅ <member> is already in the band roster.`
   - Roster removal confirmation: bold `Remove <member>?`, body `They will no longer be selected for future rehearsals.`, buttons `Remove member` and `Keep member`.
   - Duplicate tap on an already-consumed action: private alert `Already applied.`
   - Denials: callback shows the private alert `Only current chat administrators can do that.`; a command gets the group reply `Only current chat administrators can change chat setup, roster, or planning access.` State that the actor's setup or settings draft is deleted BEFORE the denial is shown, so re-promotion cannot resume it.
   - Expired draft after 30 minutes: `This setup expired after 30 minutes of inactivity. Send /setup to start again.`
   - Stale setup action: `This setup action is no longer available. Send /setup to start again.`
   - Stale settings or roster action: `This action is no longer available. Open /settings or /roster and try again.`
   - Location failure: `I couldn't determine a time zone from that location. Send a more precise location or another location in this group.`
   - Roster longer than 20 entries: deterministic alphabetical pages of 20, footer `Showing <start>–<end> of <total>`, neutral `Previous` and `Next` buttons, per-member `Remove member` preserved on each page.

   Step 2 additionally needs a `### Inspect logs` sub-block giving a runnable recipe that greps the bot service logs for coordinate-shaped content — latitude and longitude words plus a decimal-degree numeric pattern — and states that the expected outcome is zero matching lines, and that any match is an immediate FAIL of the second acceptance criterion. Also tell the operator not to paste raw coordinates into the recorded evidence when reporting a failure; report the field name and line number instead.

   Step 5 additionally needs an explicit ordering note: demote the account in Telegram group settings BEFORE the next protected interaction, verify BOTH a protected command and a protected callback, and confirm that a success that happened before demotion cannot be replayed to bypass the check.

6. `## Acceptance criteria mapping` — a markdown table with a header row and one row per acceptance criterion, four columns: an ID (`AC-1` through `AC-5`), the criterion restated from 01-14-PLAN.md Task 2, the step numbers that evidence it, and a blank result cell. Cover all five: the real group location reaches the correct actor-bound step and yields a confirmable IANA candidate; every candidate has its own action, only the selected zone reaches review and save, and no raw coordinates appear in logs or planning evidence; configuration and roster state survive the bot restart and match the committed projection; demotion takes effect at the next command or callback, discards the actor's draft, and cannot be bypassed by a prior success; message hierarchy, exact copy, inline buttons, immediate callback completion, wrapping, pagination, and safe identity all match the UI contract.

7. `## Sign-off` — the resume signal. If all six steps and all five criteria pass, the operator types `approved` to release the blocking checkpoint. If anything fails, the operator reports three things: the exact step number, the observed message or state, and the expected contract from `01-UI-SPEC.md`. State that the operator must not approve around a mismatch, and that a discrepancy blocks approval rather than being waived.

Do not add a status or completion marker that claims the verification passed. This file is the instrument, not the result.
