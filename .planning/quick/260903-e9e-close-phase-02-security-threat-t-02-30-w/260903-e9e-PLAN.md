# Quick Task 260903-e9e: Close T-02-30 with a Guarded Migration Deploy

<objective>
Close Phase 02 security threat T-02-30 by replacing the repository's bare deployment
command with one executable entry point that detects inherited schema state, runs both
required data checks, and invokes `prisma migrate deploy` only after the checks pass.

Purpose: Plan 02-09 documented the two queries and proved them manually once, but its
summary left the check as user setup. The merged deployment path still allows an inherited
database to reach the enum replacement and participant foreign key without executing the
checks first. This plan converts that non-executable instruction into a release invariant
and proves the ordering against real PostgreSQL.

Output: a guarded migration runner using the existing `pg` dependency, the package-script
wiring already consumed by CI and Compose, and deterministic integration coverage for a
fresh database plus clean and blocked inherited databases.

The committed `20260902152000_planning_participant_integrity` migration is an input to this
work, not a target for further editing. No migration SQL, Prisma schema, dependency,
lockfile, CI workflow, or Compose definition changes are in scope.
</objective>

  <action>
Start RED by extending `tests/helpers/postgres.ts` and creating
`tests/integration/migration-preflight.test.ts`. Keep every existing no-argument helper
call unchanged: the default must still apply the full migration history and run migration
status. Add an optional setup mode that starts a database with no migrations, or with all
committed migration directories lexicographically before an exact exclusive cutoff. For
the cutoff mode, build a temporary Prisma migrations tree under a unique ignored
`node_modules/.cache` directory, copy `migration_lock.toml` plus the selected migration
directories without changing their contents, write a temporary Prisma config that points
at that tree and the repository schema, run deploy and status through the existing local
CLI seam, and remove the temporary tree in `finally`. Assert that the requested cutoff
exists and that at least one migration precedes it so a typo cannot silently create an
empty baseline.

In the new integration file, use PostgreSQL 18.4 and invoke the exact supported command
`npm run db:migrate:deploy` as a child process with only the disposable `DATABASE_URL`
substituted into its environment. Cover three independent databases: completely fresh;
clean inherited immediately before
`20260902152000_planning_participant_integrity`; and blocked inherited immediately before
that migration. Seed the blocked database through SQL valid for the pre-integrity schema:
one `planning_rounds` row whose status is the legacy enum member and one
`planning_participants` row whose `membership_id` has no matching `chat_memberships.id`.
Before each absence or ordering assertion, prove the corresponding positive state: the
planning tables exist on inherited databases, the target migration is pending, and both
anomaly rows exist in the blocked fixture.

The tests must assert database effects as well as process output. A clean inherited run
must show both zero counts, exit 0, record the target migration with a non-null finish and
no rollback, remove the legacy enum label, and expose the amended composite participant
foreign key. The blocked run must capture a non-zero child-process result, show both named
counts as one, state that no migration was started, retain both fixture rows, retain the
legacy enum label, and prove no `_prisma_migrations` record exists for the target migration.
The fresh run must apply every committed migration successfully. Add a wiring assertion
that `package.json` points `db:migrate:deploy` at the guard and that CI plus Compose still
call that npm script. Run the focused file and observe it fail against the current bare
deployment command before implementing the runner.

Create `prisma/migrate-deploy.mjs` as the single supported deployment executable. Keep it
inside `prisma/` because the existing Docker migrate stage already copies that whole
directory. Use the already-installed `pg` client and require `DATABASE_URL` without ever
printing it. First query `to_regclass` for `planning_rounds`, `planning_participants`, and
`chat_memberships`: all absent means a fresh database and may proceed; all present means
an inherited database and must execute both checks; a mixed result is an inconsistent
baseline and must exit non-zero. On an inherited database, execute these statements
verbatim and independently before starting Prisma:

1. `SELECT count(*) FROM planning_rounds WHERE status::text = 'ABANDONED';`
2. `SELECT count(*) FROM planning_participants p LEFT JOIN chat_memberships m ON m.id = p.membership_id WHERE m.id IS NULL;`

Parse PostgreSQL count strings without precision loss. Always close the preflight client
before launching the migration child. If either value is non-zero, print one bounded
diagnostic naming both conditions and both counts, say explicitly that migrations were not
started and existing rows were preserved, and direct the operator to inspect/repair the
data through a reviewed backup-aware data migration before retrying. Do not print row
contents, identifiers, credentials, or the connection URL. A connection/query failure also
exits non-zero and never launches Prisma.

Only the fresh or two-zero paths may spawn the repository-local Prisma executable with
arguments `migrate deploy`, inherited stdio, and the current environment. Propagate its
exit status and signal. Do not expose a package script for raw Prisma deployment: change
only `db:migrate:deploy` in `package.json` to execute `node prisma/migrate-deploy.mjs`.
Leave `db:migrate:dev`, `db:migrate:status`, the lockfile, the amended migration, CI, and
Compose unchanged. Their existing wiring is intentional: CI proves the fresh path,
Compose's inherited volume now crosses the guard, and `tests/helpers/postgres.ts` may keep
calling Prisma directly only for disposable databases whose state that helper itself
created.
