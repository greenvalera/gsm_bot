## Gap Closure Context

This plan closes **G-01-14 / finding F-7 / broken window 5**.

Root cause (already diagnosed, do NOT re-diagnose — see `.planning/debug/denial-on-ordinary-message.md`):
both update routes in `src/telegram/handlers.ts` evaluate the administrator gate BEFORE establishing
that the update is a protected-action attempt. `authorize()` fails for any non-administrator, so the
denial is sent at `:231` / `:205` and the handler returns, never reaching the draft lookup at
`:234-235` / `:209` that decides route ownership. The correct silent no-op already exists at
`setup-service.ts:156` → `setup-handlers.ts:375` but is unreachable for non-admins. Model error:
`CHAT_READINESS_ROUTES` marks the two update routes `protectedRoute: true` exactly like the four
command routes, conflating "route that can carry a protected action" with "every update here is one".

Escape cause (N-2): `tests/integration/chat-readiness.e2e.test.ts:329, :371, :381, :384` only ever
sends `"19:30"` — a plausible wizard answer — then asserts the route must authorize first and must
deny. It certifies the defect. Both halves are corrected in the same commit as the fix.

**AC-4 constraint (resolved, binding):** draft deletion is NOT in `handlers.ts`. It is a side effect
inside `AuthorizationService.requireCurrentAdministrator` (`authorization-service.ts:45-52`), strictly
before the throw at `:53`. Delete-before-deny therefore holds BY CONSTRUCTION on all branches and
survives any reordering that keeps the protected case flowing through that method. **It breaks only
if the fix hand-rolls its own role check or moves the deletion out.** Do neither.

### The reproduction, inlined — do NOT go looking for a scratchpad file

A working reproduction was built and run during diagnosis, but it lived in a session-scoped
scratchpad directory that will NOT exist when this plan executes. Everything it established is
restated here so the regression can be written from this plan alone.

Its shape: a real grammY `Bot` with a recording `bot.api.config.use` transformer that appends
`{ method, text }` to an ordered `sent` array; the production `registerChatReadinessHandlers`
registered against a fake Prisma exposing `setupDraft.deleteMany`, `settingsEditDraft.deleteMany` and
`settingsEditDraft.findUnique`, where both `deleteMany` fakes append a marker to an ordered
`deletions` array; a real `AuthorizationService` over a role stub returning `administrator` only for
the admin id; and a `setup` stub whose `requireActive` returns an active draft or a missing one per
case. The ordering claim rests on `sent` and `deletions` being appended in real call order — preserve
that property in the port.

Three cases. The third is the ONLY gate on T-01-17-02, so it must not be dropped or merged:

1. **HYPOTHESIS.** A non-administrator sends an ordinary sentence with no draft of either kind.
   Assert `sent` is empty. This states the contract, so it FAILS today and greens on a correct fix.
2. **CONTROL.** An administrator sends the same ordinary sentence with no draft. Assert `sent` is
   empty. This PASSES today and must keep passing, so a fix that silences the route unconditionally
   is caught.
3. **AC-4 ORDERING.** A non-administrator sends a plausible wizard value while a setup draft exists.
   Assert BOTH that `deletions` contains the setup-draft deletion marker AND that the last entry in
   `sent` carries the command-denial text. Both halves are required: the marker alone does not prove
   ordering, and the denial alone does not prove the draft was discarded. Because the deletion is
   appended inside `requireCurrentAdministrator` before its throw and the reply is appended after it,
   the two arrays together pin delete-before-deny.

<objective>
Narrow the administrator gate on the two update routes so it fires only when the update actually
answers a live prompt, leaving an ordinary non-administrator message completely silent.

Purpose: In a live group the bot currently refuses every ordinary message a non-administrator sends
in reply to any bot prompt. That also made the live-demotion test non-probative, because the same
refusal appears with or without demotion.
Output: A read-only route-ownership probe ahead of authorization on `message:text` and
`message:location`, an explicit route model that distinguishes always-protected from
in-flight-only routes, and the regression that could have caught this.
</objective>
