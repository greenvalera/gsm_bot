## Gap Closure Context

This plan closes **G-01-8 / findings F-5 and F-6 / broken windows 6 and 7**, and the collateral
defect **N-1**. Two independent defects, deliberately not collapsed into one story
(see `.planning/debug/daily-boundaries-incomplete-and-unvalidated.md`).

**F-5** — `src/telegram/keyboards.ts:86` renders a plural-labelled `Edit daily boundaries` button
bound to the single field `DAILY_START_MINUTE`. `DAILY_END_MINUTE` is bound to no button anywhere,
though every other layer already works: prompt (`renderers.ts:197-200`), parser
(`settings-handlers.ts:184`), property map (`settings-service.ts:113-114`), validity check
(`settings-service.ts:136-138`), review display (`renderers.ts:216`). `settings-handlers.ts:70-81`
already mints an orphaned `DAILY_END_MINUTE` token on every dashboard render. **Window 6's file
attribution is wrong — the owner is `keyboards.ts`, not `settings-handlers.ts` (N-3).**
No migration, no service change; two buttons stay inside the recorded one-field-per-draft decision.

**F-6** — `schedule-validator.ts:42-71` enforces four rules and never anchors the rehearsal to the
daily window FLOOR. The missing predicate was never specified: `01-UI-SPEC.md:115`,
`01-PATTERNS.md:121` and `01-06-PLAN.md:102`/`:120` each enumerate the rules and all omit it. **The
code matches its contract; the contract is incomplete**, so the spec must be amended in the same
change or the defect stays re-derivable.

Escape cause (N-2): `tests/unit/schedule-settings.test.ts:25-57` places `defaultStart` above
`dailyStart` in all four assertions, mirroring the spec omission. F-5 had no gate at all — there are
zero test references to `settingsDashboardKeyboard`.

**SEQUENCING (load-bearing, binding).** The moment the floor rule lands, the already-committed live
row (`defaultStart` 1080, `dailyStart` 1140) stops validating: `getCommitted`
(`settings-service.ts:185-197`) gates on `configurationIsValid`, so `/settings` degrades to the
generic load-failure copy and `beginEdit` throws. The documented recovery — re-run `/setup` — ALSO
fails, because `beginOrResume` (`setup-service.ts:134-144`) never populates `expectedRevision`
(N-1), so `saveConfiguration` aborts at `:328` after the user walks all eight steps. **Task 2 (the
`expectedRevision` fix and the data repair) MUST land before Task 3 (the validator), or the fix
bricks the configured chat.**

<objective>
Make the daily window fully editable and make an incoherent schedule impossible to commit, without
stranding the chat that already holds an incoherent row.

Purpose: `Edit daily boundaries` collects only the start value, so the daily end is permanently
unreachable after setup (D-07 requires a separate edit action for each value). Separately, a
rehearsal that begins an hour before the window opens is currently accepted and is committed in the
production database.
Output: Two dashboard rows with a structural invariant test, a revision-safe `/setup` recovery path,
a data-repair migration, the floor predicate with boundary coverage, and the two contract documents
that omitted the rule.
</objective>
