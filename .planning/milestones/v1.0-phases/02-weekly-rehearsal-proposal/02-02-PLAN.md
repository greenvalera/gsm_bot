<objective>
Prove the whole Phase 2 architecture with one production-quality vertical slice:
an authorized user sends `/plan` in a configured chat, the bot creates a durable
week-aware planning round, posts the day card as the round's single anchor
message, and one day tap replaces that same card in place with the hourly-slot
card — crossing the command router, the planning-access policy, the extended
callback boundary, the domain service, the civil/zoned time seam, and PostgreSQL.

Purpose: the callback boundary currently hard-denies every non-administrator
before it even parses the token (`registerCallbackBoundary` calls
`requireCurrentAdministrator` unconditionally, registered with
`exhaustive: true`). 02-RESEARCH.md § Summary names this the single
highest-risk integration point in the phase: under an `ANYONE_IN_CHAT` or
`PREVIOUS_PARTICIPANTS` policy, a non-admin author can start planning and then
cannot press a single button on their own card. Proving that path end to end on
this phase's first commit is worth more than any amount of layer-by-layer
progress, because if the boundary cannot be extended safely, every later plan is
built on sand.

Output: a working `/plan` -> day card -> time card path, the complete Phase 2
schema and its committed migration, and two regression matrices that pin both the
new authorization behaviour and the unchanged Phase 1 behaviour.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram group -> `bot.command("plan")` | Untrusted, unordered updates from any chat member cross here. Identity is asserted by Telegram; authority is not. |
| Telegram group -> `callback_query:data` boundary | Any member can tap any visible inline button, including a button on someone else's card. |
| `CallbackAction.targetId` -> domain | Server-authored JSON, but treated as untrusted at parse time (a corrupt row must be an ordinary parse failure, not a throw). |
| Domain -> PostgreSQL | The correctness boundary. `sequentialize` is UX ordering only; unique constraints and expected-revision guards are the guarantee. |
