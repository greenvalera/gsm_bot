<assumption_delta_decision>
**Family:** `chosen` — a configuration value became a per-instance chosen value.
**Signal:** "The planning author can choose any day in the target week and sees the
configured default..." (assumption-delta scan 2).

**The noun that is now primary:** the **planning round's chosen schedule** —
`PlanningRound.selectedDate` + `PlanningRound.selectedStartMinute` + the round's own
snapshotted `timezone`. The round, not the chat configuration, answers "when is this
rehearsal".

**Decision: `promote`.**

`ChatConfiguration.defaultWeekday` / `defaultStartMinute` are demoted from
"the rehearsal schedule" to "one seed among several, rendered as a marker on the
round's selectors" — exactly one variant of the general case, alongside the
previous rehearsal's day/time (PLAN-05, PLAN-07) and the author's free choice
across the whole week (PLAN-04, D-05). Nothing downstream of this phase may read
`ChatConfiguration.defaultWeekday` or `defaultStartMinute` to answer when a
rehearsal happens; `startsAt` / `endsAt` derive only from the round's own civil
pair plus the round's own `timezone` snapshot (DST policy rule 5).

**Rationale:** a configuration decision did become a modeling decision. Phase 1
could treat the chat's default day/time as the schedule because there was only
ever one. Phase 2 introduces a per-round chosen schedule that routinely differs
from it, and Phases 3-5 (availability, replanning, reminders) all key off the
round. Adding the round alongside a still-authoritative configuration would leave
two answers to "when is this rehearsal" and guarantee they drift.

**Suggested (not required) invariant test:** a contract test asserting that
computing a round's `startsAt`/`endsAt` reads no `ChatConfiguration` schedule
field — so a future phase that reintroduces "the chat's default time IS the
rehearsal time" goes red instead of silently regressing.
</assumption_delta_decision>

<task type="checkpoint:decision">
  <name>Task 2: Confirm the one-way durable planning-round contract</name>
  <reversibility rating="one-way">Phase 3 reads the confirmed round and its participant snapshot to publish the availability card (D-04); Phases 4-5 read the same rows for replanning and reminders. Changing the round/participant shape after Phase 3 ships requires a data migration plus a change to the Phase 3 contract.</reversibility>
  <decision>
    Lock the durable contract that Phase 2 is about to write and Phase 3 will consume.
    Four coupled choices, presented together because they are one door:

    **(a) One `PlanningRound` row carries every wizard value.** `step`, `selectedDate`,
    `selectedStartMinute`, `anchorMessageId`, `authorUserId`, `lastActivityAt`,
    `revision`, plus a start-time snapshot of `timezone` / `durationMinutes` /
    `dailyStartMinute` / `dailyEndMinute`, plus derived `startsAt` / `endsAt`.
    - Pro: satisfies RELI-01 with no in-memory session; a concurrent `/settings` edit
      cannot retroactively invalidate an in-flight card; one row to resume.
    - Con: a wide table; adding a wizard step later means a migration.
    - Alternative: grammY `session`/`conversations`. Rejected in `.claude/CLAUDE.md`
      and fails RELI-01 outright.

    **(b) PLAN-02 is enforced by a nullable `activeWeekStart` column under a plain
    `@@unique([chatId, activeWeekStart])`.** The column equals `targetWeekStart` while
    the round is `DRAFT` and is set to NULL on confirm/abandon/supersede; PostgreSQL
    treats NULLs in a unique index as distinct, so finished rounds coexist freely.
    - Pro: the database is the correctness boundary, not application code; no Prisma
      preview flag; `migrate dev` will never drop it.
    - Con: the "active" state is encoded in two places (`status` and
      `activeWeekStart`) and they must be changed together in the same transaction.
    - Alternative: a Prisma partial index (`where:` on `@@unique`) — behind the
      `partialIndexes` preview flag, with reported drop/recreate churn; or a
      hand-written `CREATE UNIQUE INDEX ... WHERE` in a `--create-only` migration,
      which the shadow-database diff proposes to drop on every later migration.

    **(c) `PlanningParticipant` is the confirm-time snapshot and IS the Phase 3
    contract (D-09/D-11).** Rows are created inside the Confirm transaction from
    `RosterService.listActive`; there is no participant-selection wizard step.
    - Pro: one source of truth for the lineup; `PREVIOUS_PARTICIPANTS` policy reads it;
      Phase 3 knows exactly who may respond.
    - Con: reversing D-09 later means re-adding a wizard step and its callback shapes
      (CONTEXT rates that `costly`, not one-way — the snapshot column stays valid).

    **(d) `previousRehearsal()` = the most recent `CONFIRMED` `PlanningRound` for the
    chat with `startsAt < now` (Assumption A1).** One named function; Phase 4 narrows
    it to "booked" (LIFE-05) in that one place.
    - Pro: Phase 2 has no other rehearsal-shaped durable record; the markers and the
      `PREVIOUS_PARTICIPANTS` policy stay coherent with each other.
    - Con: a proposal that was confirmed but never actually booked will drive the
      PLAN-05/PLAN-07 markers and will decide who may start planning under the
      `PREVIOUS_PARTICIPANTS` policy. If the owner disagrees, the alternative is to show
      no previous-rehearsal marker at all until Phase 4 lands.
  </decision>
