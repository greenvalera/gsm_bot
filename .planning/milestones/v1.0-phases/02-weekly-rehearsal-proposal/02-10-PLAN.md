<objective>
Close the sharpest item in G-02-5: `selectDay`, `selectTime`, `back` and `takeover`
each consume the callback token with `updateMany ... consumedAt: null` and only THEN
guard on `revision`, returning `{ kind: "stale" }` when the guard fails. Prisma
commits an interactive transaction on a normal return, so the consume is durable
while the transition never happened. `confirm()` is the only one of the five that
handles this — it releases the token on that branch and its comment names the exact
symptom.

Purpose: `back()` and `takeover()` mint exactly one token each, so a lost race there
leaves a permanently dead button with no second control to escape through. The author
is left holding a card whose only remaining exit is `/plan_status`, which may itself
be inside its cooldown. `selectDay` and `selectTime` mint a set, but the same token is
still silently marked spent for a transition that did not happen, which is a lie in
the durable record whatever the card does next.

Output: one release helper shared by all five transitions, and regression tests that
ACTUALLY LOSE THE RACE — a committed competing write lands between the transaction's
round read and its guarded update — rather than asserting a happy path.

Not in scope: the confirm-time lineup snapshot and the callback_actions retention
sweep, both of which land in 02-11 and both of which touch this same file, so 02-11
runs after this plan.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Two simultaneous taps -> one durable round | Any member of the chat can generate a second update at any moment; the round row is the only arbiter. |
| Interactive transaction -> commit on return | Prisma commits on a normal return, so a refusal returned after a write is a refusal that persisted a write. |
| Card control -> its token | back and takeover mint exactly one token per step, so a token wrongly marked spent removes the only control the user has. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-33 | Denial of service | permanently dead Back and Take over buttons | high | mitigate | The lost-race branch of all five transitions now releases the token inside the same transaction, so the consume and the release commit together and the outcome is indistinguishable from never having consumed. Proven by a committed competing write landing between the round read and the guarded update, for each of the four transitions that lacked it, with the retry asserted to succeed. |
| T-02-34 | Tampering | resurrecting a token for a transition that DID happen | high | mitigate | The release is called on exactly one branch — the guarded update matching zero rows — and is a single shared helper, so there is one place for that rule to be got wrong. Two idempotency cases assert that a successful transition still leaves its token consumed and that a second use is refused with no second write. |
