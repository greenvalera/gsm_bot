<objective>
Make the thirty-minute ready-to-book announcement window a property of the notification rather than of the answer path, so `/plan_status` can no longer re-notify the whole band once a minute.

Purpose: this is gap G-01, the phase's only BLOCKER, and it is a PLAN-level hole rather than an executor deviation — `03-04-PLAN.md` Task 3 explicitly specified that only the sixty-second status cooldown applies to the announcement re-post shape. `/plan_status` is open to every member of the chat (Phase 2 D-15), so today any member can push the full "Ready to book … Time to book the rehearsal." message plus a live booking control into the group once per minute, indefinitely, for as long as the round stays unanimous. `READY_ANNOUNCE_COOLDOWN_MS`'s own docstring names this as the guarantee it exists to provide.
Output: `claimAnnouncementRepost` on `PlanningService` over a claim statement shared with `claimAnnouncement`, a slot decision in `handlePlanStatusCommand` gated on it, one new bounded log reason for the quiet fall-through, and the integration cases that would have caught the defect.
</objective>

## Recorded decisions

**D-21 — the in-window `/plan_status` for a ready-to-book round falls through to the availability card, it does not go silent and it does not edit the announcement.**
The verifier offered two remediations: fall through to the quiet anchor slot, or edit `announcementMessageId` in place. The fall-through is taken. Editing the announcement in place would re-point nothing and leave the requester's actual complaint — the card is buried under conversation — unanswered, while a silent refusal would make the phase's most open command look broken for exactly the state the band spends the most time in. The anchor slot is already the shape `/plan_status` uses for every other position, it is already rate-limited at sixty seconds by `lastStatusPostedAt`, and it carries the live answer controls rather than the booking control — so it is useful and it does not notify anybody that anything new happened. Reversibility: **reversible** — a slot literal and a log reason.

**D-21a — the claim result chooses the CARD, not only the slot.**
`repostAnchor` renders once, through `renderStep`, and `renderStep`'s non-draft branch chooses the announcement form from its own predicate — confirmed, announced, still unanimous — entirely independently of the `slot` argument, which selects only which message id is superseded and which of the two re-anchor writes runs. Gating the slot alone would therefore still `ctx.reply` a new message carrying the ready-to-book copy and the Mark-as-booked control, and would additionally re-point `anchorMessageId` at it and clear the availability card — the pointer inversion `renderStep`'s own doc comment warns against. So the claim result is threaded into the render: `repostAnchor` takes a `card` option and forwards it to `renderStep`, whose non-draft branch honours an explicit request and otherwise falls back to today's predicate, leaving `/plan`'s resumed-round caller and every other existing caller byte-identical. Reversibility: **reversible** — one optional parameter with a defaulting branch.

**D-22 — the announcement claim is short-circuited behind the ready-to-book predicate.**
The claim is attempted only when the round is confirmed, already announced and still unanimous. Claiming unconditionally would let an ordinary status re-post of a collecting round consume the window, so a unanimity reached ten minutes later would find the claim refused and would edit a message the band never received as a notification. Reversibility: **reversible**.

## Assumption-delta checkpoint (advisory, resolved here for the whole gap-closure set)

`assumption-delta scan 03` returns `detected: true` with one `chosen` signal (the ROADMAP word "custom" in "publish a custom availability card"). That signal is a false positive — "custom" there contrasts the bot's own card with a native Telegram poll and names no derived→chosen transition. The real seam is the one this plan closes, and it is a `pluralization`:

- **The noun that is now primary:** *a notifying ready-to-book message*. It is no longer "the announcement the answer path posts"; there are two doors to the same notification, and a third (a Phase 5 reminder) is plausible.
- **Decision: `promote`.** The committed claim on `readyAnnouncedAt` is promoted to the single authority for "may the band be notified now", and the answer path is demoted to one caller of it. The alternative — adding a second, path-specific gate alongside the first — is precisely the shape that produced G-01, and it would silently contradict D-18's stated intent again the next time a path is added.
- **Invariant test (accepted, Task 2):** *every message the chat receives that carries the ready-to-book copy is preceded by a committed claim on `readyAnnouncedAt`, whatever path produced it.* It goes red the instant a future phase adds a third door without a claim.
